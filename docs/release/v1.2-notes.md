# m4shlab v1.2

## Neu

- Stronger mosh on long windows. Normalized clips are now encoded with a single keyframe at frame 0 instead of a refresh every 30 frames, so the prediction chain is no longer reset once per second. A measured 74-frame mosh window now runs with no interior keyframe and still decodes 204/204 frames.
- Both normalization paths now share that cadence. Clips that fall back to ffmpeg.wasm no longer keep the old one-second refresh, so the effect strength no longer depends on which encoder the browser happened to use.
- Save and load project settings as a small `.m4settings` file, including the project name, sound state, clip speed and look, and transition values and seeds. Invalid files are rejected before the timeline changes.
- Edit the Randomize seed directly, copy it, and reproduce the same variant later with the same clips and seed.
- Read the completed merge report in a collapsed bitstream panel instead of the daily UI.
- See a dismissible notice when a reload mixed two app-shell versions; the editor stays usable until the reload is confirmed.
- Trim a clip by frames or seconds, preview the clamp at both boundaries, see the in-point on the card thumbnail, and apply the trim in one encode pass.
- Use a custom pointer on desktop, including a pressed state and a clear fallback to the system cursor on touch devices.

## Behoben

- The ffmpeg.wasm fallback encoded a keyframe every 30 frames while the WebCodecs path had already moved to a single keyframe. Measured on a 90-frame fixture: three keyframes at samples 1, 31, 61 before, one at sample 1 after. This matters most on Safari, which takes the fallback path under memory pressure.
- The browser test gate could report success without having run its checks. It now always ends with `passed N / skipped M`, names any skipped block, and exits non-zero when checks were skipped, so a gate that did not run cannot look green.
- A trim-dialog state could be cleared while the dialog was still open, because the browser delivers a dialog's `close` event as a separate task. Programmatic closes in the test suite now wait for that event. The application itself was not changed.
- Reloading from the shell notice could return the old cached shell; the page now waits for the new worker controller before reloading.
- Connector durations could keep the source frame rate after automatic normalization; they now use the normalized frame count and output time base.
- Card and import-skeleton geometry now derive from one set of CSS custom properties, so a future card change cannot desynchronise them.
- Loading a settings file that failed later in validation could partially change the project; the whole load now rolls back.
- A missing optional control could prevent the import listeners from being wired; required and optional shell elements are now checked separately.

## Grenzen

- Without periodic keyframes, seeking into the middle of a prepared clip can show a stale frame until the decoder catches up. Expect slower scrubbing on long clips.
- Single-clip Phase A mosh requires two keyframes to find a boundary. Clips normalized to a single keyframe are therefore reported as not moshable in that single-clip path; sequence merges are unaffected (this path is used by API callers such as `mosh.js`, not by the editor timeline).
- The strong-effect claim is measured, not proven for all material. The keyframe counts above come from 75- and 90-frame fixtures. Very long sources (a minute at 30 fps is 1800 frames) were not measured, and encoders may still insert their own recovery keyframes.
- The two normalization paths share the keyframe cadence but not the quality target: WebCodecs encodes with a resolution-derived variable bitrate, while the ffmpeg.wasm fallback uses constant-quality CRF 23. The same clip can therefore look slightly different depending on the path taken.
- Normalization caps the long side at 720 px. Larger clips are deliberately downscaled before processing.
- The timeline holds up to 12 clips.
- The conversion input limit is 100 MB and is a soft limit; very large files may still exhaust browser memory.
- The first load needs a network connection so the app shell can be cached.
- The ffmpeg.wasm core is fetched on demand and kept in the runtime cache; the OS may evict it under storage pressure.
- iOS can hit memory pressure during large conversions or exports, even within the stated limits.
- Audio follows the clip timeline and is not moshed. Mosh, Melt, Loop Release and Reset Pulse are picture operations.
